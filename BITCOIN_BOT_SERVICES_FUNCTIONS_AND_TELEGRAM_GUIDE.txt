1. RUNTIME TOPOLOGY AND RESPONSIBILITY
moneyflow
  Uses credential-free Binance public Spot/order-book/trade/kline data and public USD-M context. It may add optional Bitcoin-only CoinGecko/CoinMarketCap telemetry. External-provider output is explicitly advisory_only=true and affects_entry_decision=false. It writes bounded moneyflow snapshots and health.
freqtrade
  Runs the locked 1-minute IctSmcStrategy with 5-minute informative indicators. Runtime order entry is denied; it emits signed signals and a pair-seam heartbeat. Freqtrade exposes only the internal API used by Telegram and health checks. It is not the authenticated Binance order owner.
execution-sidecar
  Is the only service that receives Binance API credentials and the only authenticated Spot order owner. It validates the selected BTC pair and exchange filters, stores durable intents/state, reconciles ambiguity, manages entries and exchange-native OTO/OCO/trailing protection, handles partial fills and user-stream recovery, and defaults to simulation with entries off.
telegram-broker
  Is the owner-only private-chat control plane. It has no Binance credentials. It sends signed commands to the sidecar, calls the internal Freqtrade API, requires one-use expiring confirmation for money-affecting actions, redacts all output, and now provides a consolidated read-only /audit command.
monitoring
  Is a separate read-only API/reporting/systemd layer. It receives no Binance or trading Telegram credentials and no Docker socket. It can alert and report but cannot trade, repair, or guarantee delivery.

2. END-TO-END DATA AND CONTROL FLOW
Public Binance data -> moneyflow snapshot -> locked Freqtrade indicators/signals -> signed signal envelope -> execution-sidecar validation/reconciliation -> simulation or authenticated Spot execution -> durable SQLite/JSON/audit state.
Telegram owner -> private-chat authorization -> optional one-use confirmation -> signed command inbox or internal Freqtrade API -> result -> final redaction -> owner chat.
GitHub hosted verification -> deterministic tarball -> Oracle self-hosted runner staging -> independent root-approved full tar SHA-256 -> restricted root wrapper -> existing atomic installer/rollback -> exact four-service and application-health verification.

3. DEPLOYMENT SAFETY FUNCTIONS
The GitHub deployment job is manual, main-branch-only, simulation-only and requires SIMULATION_ONLY plus ORACLE_DEPLOY_ENABLED=true. The Oracle gha-runner account is separate from the bot deployment user, cannot read /etc/bitcoin-bot/.env, and is not in the Docker or sudo groups.
The root-owned bitcoin-bot-deploy wrapper accepts exactly preflight, simulation or verify. It rejects Testnet/live/production, requires empty Binance credentials, validates a one-use root-approved tarball SHA-256 independently of the repository checksum, safely extracts and verifies the manifest/secret scan/protected strategy hash, then calls the existing transactional installer. Approval is consumed before install so replay requires fresh administrator approval.
Use docs/GITHUB_ORACLE_DEPLOYMENT.md for the exact two-pass GitHub/Oracle procedure. Deployment success is infrastructure evidence only and cannot override the failed strategy gate.

4. TELEGRAM SETUP AND USE
Create a dedicated bot with BotFather, put its token only in /etc/bitcoin-bot/.env, and set TELEGRAM_OWNER_CHAT_ID to the numeric private-chat owner ID. Never paste either value into GitHub, logs or chat. The broker refuses a command unless both the sender user ID and private chat ID match the configured owner.
Start in EXECUTION_MODE=simulation with LIVE_TRADING_ENABLED=false, AUTO_CONFIRM=false, AUTO_PROTECTION_ENABLED=false, empty Binance keys and entries off. After the four services are healthy, send /menu in the owner private chat.

One-use confirmation behavior:
  A money-affecting command first displays CONFIRM and Cancel buttons. The callback token expires, can be consumed once, and a token-specific cancellation invalidates that exact confirmation. Replaying a used callback is rejected. Pair switching never resumes entries automatically.

5. HOW TO USE /audit
Send /audit in the configured owner private chat. It performs no sidecar command and no repair. Its only network action is the internal read-only Freqtrade GET /ping.
A healthy report requires: deployment status DEPLOYED; release validation and both container/monitoring gates passed; all four release-hash sources and both release paths consistent; configured, deployment, validation and sidecar execution modes equal; simulation flag consistent; entries_enabled=false; zero unresolved intents; an idle pair-switch state; one matching BTC/QUOTE pair across the pair, sidecar and moneyflow records; Freqtrade ping; and fresh healthy sidecar, moneyflow and Telegram files.
If ok=false, inspect the named issues, keep entries off, use /status, /deploy and /logs, then investigate on Oracle. Do not use /start merely to clear a warning. /audit reports evidence; it does not certify profitability, Binance account permissions, real fills or network reliability.

6. IMPORTANT FAILURE AND PROMOTION BOUNDARIES
Simulation may still expose software defects but cannot prove authenticated order lifecycle. Spot Test Network uses virtual assets and periodically resets. Testnet fills do not reproduce production liquidity. Real stop-limit orders can trigger without filling; cancel/replace is inherently non-atomic; network ambiguity can leave exposure uncertain. All such cases must fail closed and be reconciled.
No live promotion is authorized. The strategy must be redesigned only under a separate explicit instruction, frozen, tested on training and untouched out-of-sample data, checked for lookahead/recursive issues, exercised on Testnet, deployed through Oracle failure drills, soaked for at least 14 days, and supported by fresh signed evidence. A passing future backtest would still not guarantee profit.
