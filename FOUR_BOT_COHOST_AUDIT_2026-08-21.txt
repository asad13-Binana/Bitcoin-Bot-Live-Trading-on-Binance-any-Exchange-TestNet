AUDIT CLAIM DISPOSITION
-----------------------
1. Four-bot host-level namespace collision: CONFIRMED and fixed in the
   deployment layer. The old packages reused family-wide Compose names,
   images, paths, users, locks, units and ports.

2. Old Oracle capacity claims of 4 OCPUs/24 GB, and old single-bot plans using
   1 OCPU/6 GB, are not suitable for this four-bot design. Current official
   Always Free allowance is treated as 2 OCPUs/12 GB aggregate. This package
   requires at least 2 CPUs, 11,264 MiB reported physical memory, 3,800 MiB
   swap and 80 GiB free disk.

3. Binance user-data-stream compact expiry reason eR: CURRENTLY UNRESOLVED IN
   THE BINANA PROTECTED EXECUTION CORE. Current official Binance Spot
   documentation defines eR on executionReport. The present Binana core reads
   REST-style expiryReason but not compact eR. This was not changed because
   execution safety core is protected.

4. MAX_NUM_ORDER_LISTS scope: CURRENTLY UNRESOLVED IN THE BINANA PROTECTED
   FILTER CORE. Official Binance documentation defines MAX_NUM_ORDER_LISTS per
   symbol and EXCHANGE_MAX_NUM_ORDER_LISTS exchange-wide. Current Binana code
   counts all open lists for MAX_NUM_ORDER_LISTS. This was not changed because
   the filter/execution core is protected.

5. Binana simulation set_size fidelity: CURRENTLY UNRESOLVED IN PROTECTED
   simulation/execution code. submit still uses deterministic price=100,
   quantity=1 independently of trade_size_usdt. This does not place real
   orders, but simulation sizing is not proof of configured real sizing.

6. LIVE evidence:
   - Bitcoin current code binds and re-verifies the backtest artifact.
   - Binana current protected live-evidence code validates a declared
     artifact_sha256 format but does not itself reopen and hash the referenced
     backtest bytes. No protected-core change was made.

7. Sharia source registry: an empty committed registry is a deliberate
   fail-closed starting state. Current Binana code has automatic CoinGecko
   discovery with CoinMarketCap fallback, weekly refresh, 90-day archive and
   owner_verified=false/trade_permission=false for discovered records.
   Discovery does not self-authorise a coin.

8. CoinGecko/CoinMarketCap: the free APIs remain supported. Their exact
   per-key limits must be taken from each provider dashboard/key-info response.
   Reusing one key across independent bot budgets can exhaust the shared quota.
   The runbook therefore requires separate legal keys or an operator-verified
   combined budget. Provider failure remains fail-safe/advisory, but can reduce
   availability of Sharia source discovery.

9. Old audit main SHAs, file counts, validation dates and one-bot Oracle
   commands are historical evidence, not current deployment instructions.

10. Real authenticated TestNet, Oracle recovery/soak, Telegram delivery,
    replacement-host and fee/slippage performance evidence remain external
    gates. Source tests cannot manufacture those facts.

- Added deploy/instance_identity.sh with immutable, non-secret identity.

  installs, enables and validates the state-backup service/timer required by
  the shared host contract. A four-repository regression prevents recurrence.
- Added fail-closed rejection of legacy generic roots and Compose projects.
- Added host validation for CPUs, RAM, swap, disk, current-release symlinks,
  users, wrappers, exact running Compose projects/services and required timers.
- Added cross-instance credential checks without printing values or hashes:
  trading Telegram tokens, monitor bearer tokens, enabled monitor Telegram
  tokens, all signal/command HMAC keys, and Binance keys for every active
  non-simulation instance must not collide.
- Simulation instances must not retain Binance credentials.
- LIVE packages remain simulation by default. No LIVE-money interlock was
  removed or weakened.

CREDENTIAL RULES
----------------
- Four distinct trading Telegram bot tokens.
- Distinct monitor tokens; distinct monitor Telegram tokens when reports are
  enabled.
- Distinct signal and command HMAC keys across every bus and instance.
- Distinct Binance TestNet keys for the two active TestNet bots.
- Distinct production subaccounts and keys for the two LIVE bots.
- Withdrawals disabled; production keys restricted to the Oracle public IP.
- Real secrets stay only in four root-owned /etc/<instance>/.env files.
- CoinGecko and CoinMarketCap keys may be used on free plans, subject to the
  actual key dashboard quota and the combined request budget.

ACCEPTANCE BOUNDARY
-------------------
This change makes the repository deployment identities collision-resistant and
provides a fail-closed shared-host validator. It does not prove continuous
24/7 performance on a particular VM. Before LIVE money:

1. Install all four with LIVE packages in simulation.
2. Run sudo python3 scripts/verify_four_bot_cohost.py --host.
3. Prove both TestNet order lifecycles, including partial fill/cancel/restart
   reconciliation and no duplicate orders.
4. Run reboot, network-loss, disk-pressure, restore and all-four soak drills.
5. Prove Telegram delivery and monitor authentication.
6. Resolve or explicitly accept the protected Binana eR, order-list-scope,
   simulation-fidelity and live-evidence gaps.
7. Pass fee/slippage-aware performance gates. Bitcoin's recorded canonical
   backtest remains loss-making, so source readiness is not LIVE-money approval.
