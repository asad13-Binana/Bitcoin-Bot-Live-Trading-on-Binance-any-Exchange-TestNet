BITCOIN BOT 1.1 - GITHUB CI CORRECTION - 2026-08-08A

Confirmed defect
----------------
The first real GitHub Actions run stopped in every Python matrix job during
actions/setup-python. Pip caching was enabled without cache-dependency-path, so
the action searched only for requirements.txt or pyproject.toml. This release
uses requirements-dev.txt and nested requirement files instead, and neither of
the action's default filenames exists.

Correction
----------
Both setup-python steps in .github/workflows/ci.yml now declare the four actual
dependency input files:

  requirements-dev.txt
  requirements.services.txt
  monitoring/requirements-monitoring-dev.txt
  monitoring/requirements-monitoring.txt

tests/test_repository_hygiene.py now rejects removal, misspelling or partial
configuration of either cache-dependency-path block.

Scope and safety
----------------
No strategy, signal, execution, risk, order, pair, Telegram, Docker, systemd or
Oracle deployment logic was changed. The protected strategy and live-evidence
hashes remain unchanged. Audit ledgers and the release manifest were rebuilt in
the required order after this correction.

The existing GitHub warning that the pinned checkout/setup-python revisions
target the deprecated Node.js 20 runtime remains disclosed. GitHub currently
forces those revisions to Node.js 24, so this warning did not cause the failed
run. Action revision pins must be changed only after the exact official
replacement commits are source-verified.

Real GitHub Actions, Docker, Freqtrade and artifact results remain external
evidence and must be recorded from the corrected commit's workflow run.


BITCOIN BOT 1.1 - DEPENDENCY GATE CORRECTION - 2026-08-08B

Confirmed defects
-----------------
The second real GitHub Actions run completed the core and monitoring test suites
and the offline release verification, but the dependency gates found five
release-blocking defects:

* requirements.services.lock pinned aiohttp 3.14.1. The strict audit reported
  three known vulnerabilities and identified 3.14.3 as the fully fixed version.
* monitoring/requirements-monitoring.lock pinned rpds-py 2026.6.3, whose
  Requires-Python metadata excludes Python 3.10. That contradicted the declared
  Python 3.10-3.13 support range and stopped the Python 3.10 matrix job.
* monitoring/requirements-monitoring.lock pinned cryptography 49.0.0. The
  strict audit reported PYSEC-2026-3552 and identified 50.0.0 as fixed.
* Regenerating the monitoring lock with pip-tools 7.6.0 on Windows removed the
  `sys_platform == "win32"` marker from pywin32. The third GitHub run therefore
  tried to install the Windows-only package in all four Linux matrix jobs.
* After the marker repair, Python 3.11-3.13 passed every gate and Python 3.10
  passed its lock install and complete offline suite. Its service audit then
  showed that aiohttp 3.14.3 needs async-timeout on Python 3.10, but a lock
  generated under Python 3.13 had omitted that conditional dependency.

Correction
----------
requirements.services.txt now pins aiohttp 3.14.3 as an explicit transitive
security floor. monitoring/requirements-monitoring.txt now pins rpds-py 0.30.0
to preserve the declared four-version Python range and cryptography 50.0.0 as a
security floor. Both hash-locked dependency closures were regenerated from
those direct requirements. The Python-version
compatibility packages typing-extensions and exceptiongroup are explicit so one
hash lock remains portable across the complete matrix. async-timeout is also
explicit so the service lock is complete on Python 3.10. The setup-python cache
key now also tracks both lock files. The pywin32 platform marker is preserved
explicitly so Linux ignores that Windows-only dependency.

tests/test_repository_hygiene.py now rejects removal or drift of the three
compatibility/security pins and verifies that both lock files participate in
both dependency-cache keys. It also rejects loss of the pywin32 platform marker.

Scope and safety
----------------
This correction changes dependency constraints and generated locks only. It
does not alter strategy, signals, execution, risk, order handling, pair control,
Telegram commands, deployment mode or live-enablement logic. The full release
gate and real GitHub Actions matrix must pass again before the live repository
is pushed or the artifact is classified as release-ready.
